# signalpilot — operating contract (for humans and agents)

This is the standing guide to how this product is deployed and operated.
Instance facts (live URLs, workspace, secrets inventory) live in
[deployment.md](deployment.md), regenerated by `flows/phases/08-docs`;
this file is the contract that stays true between deployments. It is
written to give an agent with repository read access (e.g. through the
Orun MCP surface) enough context to reason about and operate the system
without any other source.

## What this system is

A multi-tenant SaaS on Cloudflare + Supabase, expressed as an Orun
component-native desired-state repo:

- **`apps/api-edge`** — the single public entry point (Cloudflare Worker).
  Routes to the fleet via service bindings; carries the idempotency KV and
  Hyperdrive (pooled Postgres) bindings.
- **`apps/*-worker`** — bounded-context Workers (identity, membership,
  projects, policy, config, events, webhooks, metering, billing,
  notifications, …). Never public; reached only through the edge.
- **`apps/web-console-next`** — the console UI, Next.js on Workers +
  Static Assets, configured against the edge.
- **`infra/terraform/*`** — data plane: Supabase projects (stage/prod),
  Cloudflare Hyperdrive, idempotency KV. **`infra/db-migrate`** — database
  migrations (plan on PRs, apply on merge).
- **`packages/*`** — shared contracts/SDK packages the apps build on.

Environments: **`stage`** and **`prod`** are fully provisioned and
deployed; **`dev` is verify-only by design** — lanes run, nothing deploys.

## Identity and tenancy

Every remote operation runs against ONE Orun workspace. Resolution order
(most specific wins): `--workspace` flag → `ORUN_WORKSPACE`/`ORUN_ORG` env
→ `intent.yaml` `execution.state.workspace` / `.project` → the repo's
cloud link → `orun workspace use` selection.

- This repo DECLARES its tenancy in `intent.yaml` (`workspace:` +
  `project:` under `execution.state`) — committed, enforced, and what CI
  uses. Do not remove these lines; headless credentials depend on them.
- `orun workspace <ws-id-or-slug>` resolves any workspace's identity
  (works with user sessions and workspace-scoped `ORUN_TOKEN`s alike).
- Project SLUGS in the intent are resolved to `prj_…` ids by the CLI
  (orun ≥ v2.52.4). The CI lane pin in `.github/workflows/ci.yml` must
  stay ≥ v2.52.4.

## How deployment works

1. Merge (or push) to `main`.
2. CI (`.github/workflows/ci.yml`) runs `orun plan --changed` — only
   components whose files changed are planned — then fans each planned
   job into a matrix lane running `orun run --remote-state` with
   credential-free OIDC auth (the exchange resolves this repo's bound
   workspace/project server-side).
3. Terraform state lives in the Orun Cloud HTTP state backend — no local
   state, no cloud-vendor state buckets.
4. **The convergence run is the deployment.** A green run means every
   planned lane applied. Failed lanes are retried with
   `gh run rerun --failed` (the bootstrap flows automate 3 resumes).

Caveats that matter:

- A push that touches NO component files plans ZERO lanes — that run is
  green but deployed nothing. Never treat "latest run green" as "system
  converged"; assert outcomes (URLs, published secrets) instead. The
  phase workflows' `verify` steps are the pattern to copy.
- GitHub Actions billing exhaustion presents as failing lanes with NO
  logs anywhere; the real message is only in the check-run ANNOTATIONS
  (`gh api repos/<o>/<r>/check-runs/<id>/annotations`).

## Secrets model

- **Brokered provider secrets** (project rung): `CLOUDFLARE_API_TOKEN`,
  `CLOUDFLARE_HYPERDRIVE_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`,
  `SUPABASE_ACCESS_TOKEN`, `SUPABASE_ORG_ID` — pointers minted per-run
  from the workspace's integration connections. No long-lived values at
  rest; nothing to rotate by hand.
- **Job-output secrets** (environment rungs): `WIRING_*`,
  `SUPABASE_PROJECT_REF`, `SUPABASE_DB_URL`, `SUPABASE_DB_PASSWORD` —
  published by the infrastructure terraform; deploy lanes resolve them to
  wire worker bindings (KV ids, Hyperdrive ids, database URLs).
- Inspect by NAME only: `orun secrets list --org <ws> --project` and
  `--env stage|prod`. No tooling in this repo ever prints a secret value,
  and no document in `ai/context/` may contain one.
- Post-bootstrap runtime secrets (OAuth keys, Stripe, …) are seeded with
  `orun secrets set <KEY> --org <ws> --env <env>` — wire-now-seed-later;
  nothing blocks on them.

## Verifying the system (do this, not vibes)

```bash
# the four public surfaces (also recorded, probed, in deployment.md)
curl -s -o /dev/null -w '%{http_code}\n' https://signalpilot-api-edge-stage.<subdomain>.workers.dev/health
# 2xx–4xx = alive (401/403 is "deployed, unauthorized"); 5xx/timeout = not deployed

# published wiring (names only)
orun secrets list --org <ws> --env stage

# workspace readiness (integrations + allow-list + project resolution)
orun integrations list --org <ws> --json && orun cloud check --org <ws>
```

## Common operations

| task | how |
|---|---|
| deploy a change | merge to `main`; watch the run; failed lanes → `gh run rerun --failed` |
| re-verify live state + refresh docs | run the docs flow (below); idempotent |
| add a runtime secret | `orun secrets set <KEY> --org <ws> --env <env>` |
| resolve workspace identity | `orun workspace <ws-id-or-slug>` |
| check integrations | `orun integrations list --org <ws> --json` |
| custom domain | run the domain flow once the zone exists, then the docs flow |
| headless/CI credentials | `ORUN_TOKEN` (workspace-scoped) + `GITHUB_TOKEN` |

The ops flows (docs refresh, domain, and the original deployment phases)
are versioned workflows run by remote reference — from anywhere, with the
two tokens above exported:

```bash
orun workflow run github:sourceplane/lumen@main//flows/phases/08-docs/workflow.yaml \
  --set workspace=<ws> --set repo=<owner/name>     # docs refresh
orun workflow run github:sourceplane/lumen@main//flows/phases/07-domain/workflow.yaml \
  --set workspace=<ws> --set repo=<owner/name>     # custom domain
```

Every flow is idempotent — re-running a completed one is a no-op that
re-verifies.

## Evolution

Structural changes (new workers, infra components, packages) follow the
same contract that deployed everything here: land the change as a PR,
merge, and the convergence run applies it in dependency order. The ops
flows above re-verify and re-document the system after any change.
